# Changelog

All notable changes to Verifiable Practice will be documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html) for tagged releases.

## Unreleased

- Define recoverable revisions, byte-exact recovery and audit references; replace preservation/container metaphors throughout active audit guidance. Tags, content identity, custody and recovery evidence have separate stated roles.

### Changed

- Standard1.2 separates reproducibility evidence, provenance identifiers and disposable working resources. Executable digests do not mandate binary retention; specific byte obligations need purpose/consumers/period. Preserve source/patches, reproduction specifications and raw results with environment limits; byte recovery, build reconstruction and experimental reproduction remain separate claims.

- Scale assurance by A–E consequence levels, including one change/check for D and commit-message-only E, with trigger-only D/E review.
- Require content-addressed immutable revision history and a verified recovery replica. Audit references contain commit/scope/replica locators, never copied source or nested earlier audit references.
- Prune historical evidence copies and detailed self-adoption records from the working tree after an actual baseline restore; retain one summary and immutable custody locators. Rewrite current views for a cold reader.


### Removed

- Dedicated constrained-English concept and playbook, their routes and active
  references. Ordinary-English requirement review now connects consequential
  ambiguities, actor/condition/failure meaning and observable checks to the
  existing planning, authority and evidence records.

### Added

- Full project quality management identity and lifecycle in README, WHY,
  AI skill discovery/routing and explanatory guides, including quality planning,
  control, independent assurance, improvement and human/AI responsibilities.
- Sourced content-quality assessment and documented communication choices,
  preserving the distinction between epistemic foundations, management
  authority, product quality and record conformance.

- Prospective adoption of VP records in this repository: current mandate,
  charter, stage, choices, coverage, preserved failures and independent audit.
  Missing pre-adoption history remains explicitly unknown.

### Fixed

- Non-disappearing caller validation in the Python transfer illustration,
  accurate email-example outcomes, selective-loading guidance, AI-owner
  applicability and candidate syntax evidence in the document trace.

- Explicit Project Audit and Code Audit kinds, mandatory clarification and
  waiting for ambiguous audit requests, separate reports/verdicts and routing
  scenarios; code reports have a distinct default filename.

- Actor-neutral ownership: human or AI owners with explicit mandates,
  decision limits and handoff; working-AI record keeping and independent
  assessment also cover AI-owner decisions.

- Independent record auditor/working AI role contract, audit references,
  finding IDs, worker response events and fresh closure audits; request and
  response templates, role boundaries and adversarial scenarios derived from
  Medic/Pythia while retaining portable Markdown directory handoff.

- Proposed Markdown-only project planning and records standard: stable IDs,
  stages, decisions, hypotheses, build/run provenance, revision coverage,
  finite validity, revalidation, retention and audit requirements.
- Copyable project/operation templates, an execution playbook, design-choice
  provenance, worked traces and adversarial evaluation scenarios informed by
  parallel GC and Honest and generalised for different project types.

- Community health files and GitHub contribution templates.
- Vendor-neutral root skill with progressive reference routing.
- Core concepts for goals, falsifiability, rhetoric, honest reporting, verification, human–AI responsibilities, precise technical language, and engineering standards.
- Operational playbooks for review, audit, investigation, debugging, discovery, recovery, and document work.
- Human-facing documentation for the framework and its use.
